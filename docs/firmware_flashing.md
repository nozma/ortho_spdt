# ファームウェアの書き込み手順

このリポジトリでは、エージェントが準備・バックアップ・UF2転送・検証を担当し、
ユーザーが物理キー `QK_BOOT` の押下と必要なUSB差し替えを担当する。
GUI操作は原則使用せず、Vialの設定取得・復元はUSB Raw HID経由で行う。

## 確認済みの構成と制約

- RP2040、左右それぞれにUSB接続可能。通常のPC接続は右手側。
- USB接続されている側が書き込み対象。左右間ケーブル経由で反対側へUF2は転送できない。
- VID/PIDは `0xFEED/0x0000`、Vial UIDは `a18b9b77327e7a6c`。
  実行前に現在の `keyboard.json` と `config.h` にも照合する。
- Vial Raw HIDインターフェースは usage page `0xFF60`、usage `0x61`。
  キーボード・マウス用インターフェースを操作しない。
- 現在の固定版Vial QMKでは、`VIAL_INSECURE = yes` のビルドに
  `id_bootloader_jump` の処理が組み込まれない。実機でも `0xFF`（未処理）の応答を確認済み。
  USBコマンドでの移行や解除を繰り返さず、物理キーを使用する。
- 2026-11-25時点の実機では、左右それぞれの保存キーマップに
  レイヤー4・matrix `[4, 0]`（右側の最上段・左端）の `QK_BOOT` がある。
  レイヤー4への移行は右 `L` または `;` の長押し。保存キーマップは変更され得るので、
  毎回実機から読み戻して押下位置・レイヤーへの入り方を確認する。
  リポジトリの `keymap.c` の配置から決めつけない。
- 左右間ケーブルを接続していれば、USBを左手側へ接続しているときも右側のキーで移行できる。
  片側単独で作業する場合は、その側だけでレイヤー移行と `QK_BOOT` 押下ができる必要がある。

## 1. 準備と対象側への接続

1. 書き込み対象（左／右）、ソースのコミット、利用するUF2を確認する。
2. `scripts/local_check_vial.sh` と `scripts/local_build_vial.sh` の成功を確認する。
   出力先は既定の `.vial-qmk/.build/` を使う。
3. 左へは `split_ortho4x6_vial_left.uf2`、右へは `split_ortho4x6_vial_right.uf2` を使う。
   UF2には左右識別の初期化指定が入るため、取り違えない。
   SHA-256、UF2ブロック、RP2040のfamily ID、書き込みアドレス範囲も確認する。
4. 対象側へUSBを接続する。左右間ケーブルは接続したままでよい。
   差し替えが必要な場合は、まずUSBの差し替えだけを依頼し、まだ `QK_BOOT` は押させない。

## 2. 対象側の設定をバックアップ

左右の保存設定は独立している。片側のバックアップを反対側に流用しない。

- 対象のHIDインターフェースとUIDを確認する。複数候補がある場合は停止する。
- 設定取得時はGETコマンドだけを許可する。設定のSET、リセット、解除、ブートローダー移行を送らない。
- 全レイヤーのキーコード、レイアウトオプション、マクロバッファ、Tap Dance、コンボ、
  Key Override、対応する全QMK設定を取得する。将来エンコーダー等を追加した場合はそれらも対象にする。
- 2回読み取り、結果が一致することを確認する。
- `.vial-qmk/backups/` 配下へ側・日時を区別して保存する。
  Vial互換 `.vil`、生データ、GET通信記録、検証情報・ハッシュを残す。
  個人の設定やマクロをGitへ追加しない。
- `.vil` の生成は公式Vialの保存形式・数値キーコード対応に合わせ、
  ハードウェアへ書き戻さずに復元処理のオフライン検証を行う。
- `tb.c` の独自EEPROM設定（CPI、回転、ゲイン、gamma、モード、加速度等）は
  現在読み取りAPIがなく、標準Vialバックアップには含まれない。
  これらの保持・復元を確認できたと報告しない。必要なら事前にユーザーへ設定を控えてもらう。

前回の補助スクリプトは `.vial-qmk/backups/`、依存は一時Python環境に置いてあり、Git管理外である。
次回存在することを前提にせず、処理内容と依存を確認して再利用または再作成する。
今回使用した `hidapi` はPyPIのPythonパッケージ。`hid` パッケージ単体は
ネイティブライブラリ不足で動かなかった。USBアクセスがサンドボックスで拒否される場合は、
必要なアクセス権限を求める。GUIへの切り替えやアプリ許可の再試行で回避しない。

## 3. QK_BOOTの押下とUF2ドライブの監視

**押下後のチャット返信・選択肢の送信を、書き込み開始の条件にしない。**

レイヤー移行や `QK_BOOT` の操作でチャットの選択肢が閉じることがあり、
ブートローダー中はこのキーボードから文字入力できない。
次回以降は、エージェントがUF2ドライブの出現を監視する方式で進める。

1. 対象UF2・バックアップ・書き込み権限を確認し、既存の接続ボリュームを記録する。
2. 有限時間の監視処理を開始してから、ユーザーへ
   「USBは対象側のまま、指定した `QK_BOOT` を押してください。返信は不要です」と案内する。
   ユーザーが案内を読めるよう、ツールは短いyieldで戻す。
3. macOSでは `/Volumes` に新しく現れるUF2ボリュームを監視する。
   1回の待機は60秒以内に区切り、検出できなければ状況を伝えて待機を延長する。
   期限切れ・対象不明の状態でコピーしない。
4. 単一の新規ボリュームと `INFO_UF2.TXT` を確認する。
   確認済みの実機表示は以下。文字列 `RP2040` の存在を条件にすると検出に失敗する。

   ```text
   UF2 Bootloader v3.0
   Model: Raspberry Pi RP2
   Board-ID: RPI-RP2
   ```

   ボリューム名は今回 `RPI-RP2` だったが、名前だけで対象を判断しない。
   HIDのUIDはブートローダーの情報には引き継がれないので、
   対象側へのUSB接続・押下操作・新規ボリューム出現の対応を確認する。
5. 新規の対象を検出したら、チャット返信を待たず対応するUF2を1回だけコピーする。
   コピー・flushを確認する。UF2受理直後にボリュームが消える場合があるため、
   コピー元・コピー先のハッシュ比較だけを完了条件にしない。
6. ボリューム消失とVial HIDの再接続を確認する。再接続できない場合は
   成功扱いにせず、状況を調べる。追加コピーや再書き込みを盲目的に行わない。

2026-11-25の実績は「物理キー押下→エージェントがUF2転送→再接続確認」で左右とも成功。
同日は押下後にユーザーが返信していたため、**返信不要の自動監視方式そのものはまだ実機未検証**。
次回は上記監視方式で進め、その結果を区別して報告する。

## 4. 更新確認と設定の復元

1. 再接続したデバイスのUIDと、ファームウェア内のVial定義を確認する。
   書き込んだソースの `vial.json` と比較する等、新しい版であることを確認する。
   VID/PIDやUIDだけではファームウェア更新を証明できない。
2. 全Vial設定を読み戻し、**同じ側の更新直前バックアップ**と比較する。
   書き込み成功だけで「設定を保持した」と判断しない。
3. 差分があれば、初期化なのか意図した形式変更なのかを切り分ける。
   バックアップが互換で、ユーザーの設定を維持するために必要な差分だけを復元する。
   復元前にも現在値が復元計画と一致するか確認し、他の設定を上書きしない。
4. 復元した項目を個別に読み戻し、さらに全設定を比較する。
   マクロ・コンボ等も含め、最終的に何が一致したかを記録する。
5. 2026-11-25の更新では、右側は25キーとQMK設定ID 8、左側はレイヤー4の
   `QK_BOOT` 1キーが初期値に戻った。バックアップから復元して一致を確認した。
   これは過去の実績であり、次回も同じ差分になるとは限らない。
6. 側、コミット、UF2のSHA-256、転送先、前後バックアップ、比較・復元結果を
   `.vial-qmk/backups/` に保存し、ユーザーへ完了状況と未確認事項を伝える。

## 5. 左右の切り替えと実機テスト

- 反対側を更新するときは、USBをその側へ差し替えてから手順2以降を繰り返す。
- 左側更新後は、必要に応じて通常の右側USB接続へ戻す。
- キー・レイヤー・左右トラックボール・ゲイン/CPIの使用感はユーザーに実機確認してもらう。
  HID再接続や設定一致だけで機能確認完了としない。
